## 3. 発見した不具合と修正

| # | 症状 | 原因 | 修正（コミット） |
|---|------|------|------------------|
| 1 | 初回デプロイが `AwsEndpointSg: Fn::Select: the index 0 is out of bounds` で失敗 | SG の IPv6 ルールが `Vpc.Ipv6CidrBlocks` を参照しているのに、IPv6 CIDR の関連付けへの依存がなかった。cdkd は並列に作るため空の配列を読んだ（サブネットには依存があった） | `AwsEndpointSg` に依存を追加。「`Ipv6CidrBlocks` を読むリソースはすべて `VpcIpv6Cidr` に依存する」テストを追加（`100c25a`） |
| 2 | `Ec2MessagesEndpoint` の作成が *doesn't support this IP address type dualstack* で失敗 | ap-northeast-1 の `ec2messages` は `SupportedIpAddressTypes = [ipv4]`（ほかの ECR / Logs / SSM / S3 は dualstack 対応） | `ec2messages` だけを IPv4 で作る。SSM Agent 3.3.40 以降は `ssm` と `ssmmessages` だけで動くので、IPv6 のみのモードへの影響はない（`b9f4f92`） |
| 3 | S-0 の基準値タスクが `mkdir: cannot create directory 'results': Permission denied` で終了し、数値が出ない | Fargate のバインドボリュームは root:0755 で作られ、非 root（UID 12345）の k6 が書き込めない。イメージ側でディレクトリを chown しても引き継がれない（1 回目の修正 `10f693c` は実機で効かなかった） | root の init コンテナ（`essential: false`、ルートは読み取り専用、capabilities は CHOWN 以外すべて drop）がボリュームを chown し、k6 は `dependsOn: SUCCESS` で起動する。Fargate は capabilities の `add` を SYS_PTRACE 以外受け付けないため、drop のリストで表現した。テストを追加（`607af47`、`b0f51e0`） |
| 4 | 承諾後も `pl-http` が `A=0 AAAA=0` / timeout | X-2 のために承諾 **前** にプローブすると、VPC のリゾルバーが NXDOMAIN をキャッシュする。外からは解決できるのに、利用側 VPC の中では **承諾から約 9.7 分（available になってから約 9 分）** 解決できなかった | 手順の問題としてドキュメントに追記（X-2 とトラブルシューティング、日英）。S-1 の前に `dig +short AAAA $PL_DNS` で確認する |

### 運用上の注意（cdkd）

- 実行中のデプロイを中断すると、cdkd の **状態と実際のリソースがずれる** ことがあった。状態には ECR API / Logs / S3 ゲートウェイのエンドポイントがあるのに AWS には存在せず、サブネットが関連付いたルートテーブルは状態にない、という状態になった。症状は「負荷生成 EC2 の `dnf` と ECR が timeout」。
  `npm run destroy` → 再デプロイで解消した（トラブルシューティングに追記）。
- 中断したプロセスのロックは残る。プロセスがないことを確かめてから `npx cdkd force-unlock <stack>` で解除した（ガイドの記載どおり）。
- 長いデプロイや計測は、端末の切断で止まらないように `setsid nohup` で実行するのが安全。

## 4. セキュリティのシナリオ

### プローブの結果（IPv6 / IPv4 とも同じ結果）

| target | 未承諾（X-2） | trusted | 信頼しない SG（X-1） | iam-required（X-3） |
|--------|---------------|---------|----------------------|---------------------|
| pl-http | ✗ NXDOMAIN（`A=0 AAAA=0`） | ✓ 200 ※ | ✗ timeout | ✓ 200 |
| lattice-http | ✓ 200 | ✓ 200 | ✗ timeout | **✗ 403** |
| lattice-https | ✓ 200 | ✓ 200 | ✗ timeout | **✗ 403** |
| lattice-https-sigv4 | ✓ 200 | ✓ 200 | ✗ timeout | ✓ 200 |
| s3gw-data | ✗ 403（テスト用オブジェクトのアップロード前） | ✓ 200 | **✓ 200** | ✓ 200 |
| s3gw-outside | ✗ 403 | ✗ 403 | ✗ 403 | ✗ 403 |
| s3if-data | ✗ 403（同上） | ✓ 200 | ✗ timeout | ✓ 200 |
| s3if-outside | ✗ 403 | ✗ 403 | ✗ timeout | ✗ 403 |

※ 承諾直後のプローブではまだ NXDOMAIN で、ネガティブキャッシュが切れた後（`trusted-after-dns`）に 200 になった（3. の #4）。

- **X-1**：SG を変えるだけで、ENI を持つ経路（PrivateLink、Lattice の関連付け、S3 インターフェイス）はすべて timeout になった。**S3 ゲートウェイだけは 200 のまま**。ゲートウェイはルートテーブルのエントリで SG がないため、制御はポリシーで行うことになる。
- **X-2**：エンドポイントサービスの許可プリンシパルは自アカウントのみ（`arn:aws:iam::<ACCOUNT_ID>:root`）。承諾から `available` までは **38 秒**。
- **X-3**：Lattice のアクセスログでは、匿名の呼び出しが `403 / authDeniedReason=Service / callerPrincipal=Anonymous`、署名付きの呼び出しが `200 / callerPrincipal=arn:aws:sts::<ACCOUNT_ID>:assumed-role/v6lab-consumer-LoadgenRole-…` と記録された。
- **X-5**：外部（インターネット）からデータ用バケットと外部バケットを読むと、どちらも **403**（バケットポリシーの `aws:SourceVpce`）。VPC の中からでも `*-outside` は 403（エンドポイントポリシー）。データ境界は二重に効いている。
- **X-6**：両 VPC とも `10.0.0.0/16` のまま、3 つの経路はすべて動いた。

## 5. スピードのシナリオ

### S-0 / S-1 遅延（1 KiB、接続の再利用あり、IPv6、ms）

| 経路 | p50 @100 | p99 @100 | p50 @500 | p99 @500 | p50 @1000 | p99 @1000 | S-0 からの p50 の増分 |
|------|---------:|---------:|---------:|---------:|----------:|----------:|----------------------:|
| S-0 基準値（NLB、VPC 内、n=1） | 1.81 | 3.70 | 1.84 | 3.65 | 1.84 | 3.59 | 0 |
| PrivateLink（n=3） | 2.11 | 4.04 | 1.97 | 3.80 | 1.97 | 3.74 | **+0.13〜0.30** |
| Lattice HTTP（n=3） | 4.49 | 6.48 | 4.27 | 6.27 | 4.17 | 6.24 | **+2.33〜2.68** |
| Lattice HTTPS（n=3） | 4.68 | 6.68 | 4.36 | 6.44 | 4.21 | 6.27 | **+2.37〜2.87** |
| S3 ゲートウェイ（n=3） | 24.89 | 40.96 | 24.80 | 41.54 | ― | ― | ― |
| S3 インターフェイス（n=3） | 26.05 | 57.51 | 25.91 | 56.88 | ― | ― | ― |

- 3 回の範囲は狭い（例：PrivateLink @500 の p50 は 1.93〜1.99、Lattice HTTP @500 は 4.24〜4.32）。経路の差（約 2.3 ms）は回ごとのばらつきより十分大きい。
- 接続を再利用していれば、Lattice の HTTPS と HTTP の差は p50 で 0.04〜0.19 ms と小さい。
- 1000 rps まで、どの経路も p99 は悪化しなかった。

### S-2 リクエストごとに新しい接続（IPv6、ms、p50）

| 経路 | 負荷 | 接続 | TLS | 合計（`http_req_duration`） | 接続 + TLS + 合計 | S-1 の合計（再利用あり） |
|------|-----:|-----:|----:|----------------------------:|------------------:|-------------------------:|
| PrivateLink | 100 | 2.76 | ― | 2.11 | **4.87** | 2.11 |
| PrivateLink | 300 | 2.54 | ― | 2.05 | **4.59** | 1.97（@500） |
| Lattice HTTP | 100 | 0.59 | ― | 4.78 | **5.37** | 4.49 |
| Lattice HTTP | 300 | 0.47 | ― | 4.46 | **4.93** | 4.27（@500） |
| Lattice HTTPS | 100 | 0.67 | 1.87 | 4.67 | **7.21** | 4.68 |
| Lattice HTTPS | 300 | 0.47 | 1.73 | 4.43 | **6.63** | 4.36（@500） |

- k6 の `http_req_duration` は接続と TLS を含まないため、1 リクエストの実質的なコストとして「接続 + TLS + 合計」を併記した。
- **PrivateLink は TCP の接続だけで 2.5〜2.8 ms**（リクエスト本体と同じくらい）。新しい接続の SYN がエンドポイント → NLB → タスクまで往復するため。
- **Lattice は接続が 0.5〜0.7 ms と短い**。TCP は利用側の近くにある Lattice のプロキシで終端される。そのかわり HTTPS では TLS が 1.7〜1.9 ms かかる。
- 接続を再利用しないと、PrivateLink では 1 リクエストあたり約 2.6 ms、Lattice HTTPS では約 2.3〜2.5 ms 増える。これは **PrivateLink と Lattice の差（約 2.3 ms）と同じくらい**。

### S-3 IPv6 と IPv4（500 rps、n=1、ms）

| 経路 | IPv6 p50 / p99 | IPv4 p50 / p99 | 差は回ごとのばらつきの範囲内か |
|------|----------------|----------------|--------------------------------|
| PrivateLink | 2.01 / 3.80 | 2.04 / 3.86 | 範囲内（差 0.03 ms） |
| Lattice HTTP | 4.24 / 6.84 | 4.34 / 7.07 | ほぼ範囲内（差 0.10 ms ≒ 2%） |
| S3 ゲートウェイ | 24.96 / 40.62 | 24.75 / 40.80 | 範囲内（差 0.21 ms、IPv4 のほうが速い） |

Flow Logs（利用側 VPC、80/443、egress）では、計測中のトラフィックはほぼすべて IPv6 だった（`pkt-srcaddr` が IPv6 の記録：約 3.16 GB、IPv4：約 36 MB で、IPv4 は S-3 の IPv4 の回とプローブの分）。
S3 ゲートウェイの通信は `traffic-path = 7`（ゲートウェイ VPC エンドポイント経由）として記録された。Flow Logs は集計の時点で S-4 の途中までしか届いていなかったため、量は参考値。

### S-4 スループット（1 MiB、MiB/s、n=1）

| 経路 | 32 VUs | 64 VUs | p50 @32 / @64（ms） | 限界の要因（推定） |
|------|-------:|-------:|--------------------|--------------------|
| PrivateLink | 1475 | 1475 | 17.1 / 34.8 | **クライアント**（c7i.xlarge の最大 12.5 Gbps ≒ 1490 MiB/s に到達） |
| Lattice HTTP | 1101 | 1136 | 23.4 / 42.7 | **経路**：VU を倍にしても伸びず、遅延だけが倍になった |
| S3 ゲートウェイ | 1068 | 1472 | 29.4 / 39.2 | 64 VU でクライアントの上限 |
| S3 インターフェイス | 992 | 1460 | 31.3 / 40.6 | 64 VU でクライアントの上限 |

- 1 回 1 分の計測で、EC2 のバースト帯域を使っている可能性がある（c7i.xlarge の **ベースライン帯域は最大値より低い**）。長時間の転送では数値が変わりうる。
- PrivateLink は、0.5 vCPU のタスク 2 つの構成でもクライアントの上限まで出た。Lattice の約 1.1 GiB/s が Lattice 自体の上限なのか、ターゲット（タスク）側の制約なのかは、この 1 回だけでは切り分けていない（`-c desiredCount=4 -c taskCpu=1024` での再計測が次の課題）。

## 7. 仮説の確認

| 仮説 | 確かめられたか | 根拠 |
|------|----------------|------|
| H1 PrivateLink の追加遅延がいちばん小さく、Lattice は L7 の分だけ増える | **確認** | p50 の増分：PrivateLink +0.13〜0.30 ms、Lattice +2.3〜2.9 ms（S-0、S-1） |
| H2 IPv6 と IPv4 で意味のある差はない | **確認** | 差は 0.03〜0.21 ms で、ばらつきの範囲内（S-3） |
| H3 接続を再利用しない HTTPS のコストは、経路の違いより大きい | **条件付き** | 新しい接続のコスト（+2.3〜2.6 ms）は、経路の差（約 2.3 ms）と **同程度**。「より大きい」とまでは言えない。PrivateLink は TCP の接続が、Lattice は TLS が効く（S-2） |
| H4 S3 のゲートウェイとインターフェイスの遅延は同程度。ゲートウェイは無料 | **条件付き** | p50 はほぼ同じ（24.8 / 25.9 ms）だが、**p99 はインターフェイスのほうが 16 ms 悪い**（41 / 57 ms）。スループットは 64 VU でどちらもクライアントの上限（S-1、S-4） |
| H5 新しい利用者がつながるのは Lattice がいちばん速い | **条件付き** | 機械の時間だけなら PrivateLink（6 + 38 秒）は Lattice（74 秒）より速い。人の承認と、承認前に名前を引いた場合のネガティブキャッシュ（約 9.7 分）を入れると逆転する（S-6、X-2） |
| H6 呼び出し元ごとに提供側が判断できるのは Lattice だけ | **確認** | PrivateLink では `remote` が NLB のアドレスのみ。Lattice はヘッダーとアクセスログに送信元 VPC とプリンシパルが出る（X-3、X-4） |
| H7 エンドポイントポリシーで別のバケットへの持ち出しを止められる | **確認** | バケットポリシーがエンドポイントを許可していても、`*-outside` はゲートウェイ / インターフェイスとも 403（X-5） |

## 8. 実施しなかったこと・ガイドとの違い

- **予算アラート（1.3）**：通知先のメールアドレスが必要なため作成していない。その日のうちに削除することでコストを抑えた。
- **5. IPv6 のみのワークロード**、**S-5（スケール時のふるまい）**：任意の項目のため未実施。
- **計測時間**：各負荷 1 分（既定 2 分）。S-0、S-2、S-3、S-4 は 1 回だけ。スライドに載せる数値は、ガイドの「5 回の中央値」で取り直すこと。
- **S-0 の実行時刻**：S-0 は不具合 #3 の修正後、ほかのシナリオが終わった 13:03〜13:11 に実施した（同じ NLB / タスク、ほかの負荷はなし）。
- **アカウント全体の設定**：ECR のレジストリスキャン（push 時）を ap-northeast-1 で有効にした。cdkd のアセット用バケット / ECR リポジトリは残している（`npx cdkd gc` / `npx cdkd bootstrap --destroy` で消せる）。
