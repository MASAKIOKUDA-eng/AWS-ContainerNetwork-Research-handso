### スライド 2 — なぜ今か（0:30–1:30）

**スライド**
- パブリック IPv4 アドレスは有料（2024 年 2 月〜）
- ECS が IPv6 のみのタスクに対応（2025 年 9 月）
- S3 ゲートウェイエンドポイントが IPv6 に対応（2025 年 11 月）
- → コンテナで「IPv6 前提」が現実的になった

**話すこと（訳）**
> この話ができるようになったのは、3 つの変化があったからです。
> 1 つ目、パブリック IPv4 アドレスはすべて料金がかかるようになりました。
> 2 つ目、Amazon ECS は 2025 年 9 月から、IPv6 のみのサブネットでタスクを動かせます。
> 3 つ目、2025 年 11 月に S3 ゲートウェイエンドポイントが IPv6 に対応しました。
> もう「IPv6 を使えるか」ではなく「どう設計するか」が問いです。

### スライド 3 — 本当の課題（1:30–2:30）

**スライド**
- IPv6 を有効にするのは簡単
- 難しいのは VPC やアカウントをまたぐサービス間通信
- どこもかしこも 10.0.0.0/16
- 3 つの部品：PrivateLink / VPC エンドポイント / VPC Lattice

**話すこと（訳）**
> VPC に IPv6 の CIDR を足すのはワンクリックです。難しいのはそこではありません。
> 難しいのは接続です。チームもアカウントもたくさんあって、みんな 10.0.0.0/16 を使っています。
> AWS には、IPv4 の重複を気にしなくてよい部品が 3 つあります。
> PrivateLink、AWS サービス向けの VPC エンドポイント、そして VPC Lattice です。
> どれを使うべきか。測るためにハンズオン環境を作りました。

### スライド 4 — ハンズオン環境（2:30–4:00）

**スライド**
- [02-architecture.md](02-architecture.md) の構成図
- VPC は 2 つ、どちらも 10.0.0.0/16、インターネットには一切出られない
- 同じ ECS タスクを PrivateLink の後ろと Lattice の後ろに
- k6 の負荷生成。AWS CDK のアプリを cdkd でデプロイ。すべて GitHub で公開

**話すこと（訳）**
> これが環境です。VPC は 2 つ。IPv4 の CIDR は同じです。わざとそうしています。
> インターネットゲートウェイも NAT もありません。外に出る道は、測りたい経路だけです。
> 提供側では同じコンテナを 2 つ動かしています。1 つは PrivateLink のエンドポイントサービスの後ろ、もう 1 つは VPC Lattice の後ろです。
> 利用側では k6 の負荷生成が、それぞれの経路を IPv6 で呼びます。
> すべて AWS CDK で、cdkd を使って約 `[RESULT]` 分でデプロイでき、GitHub にあります。自分のアカウントで動かせます。

### スライド 5 ✂ — 設計のプラクティス：サブネットの層（4:00–5:00）

**スライド**
- エッジのサブネット：デュアルスタック（NLB、エンドポイント）
- ワークロードのサブネット：デュアルスタック → IPv6 のみ
- ECR / Logs / SSM / S3 のデュアルスタックの VPC エンドポイント
- 「IPv6 前提」≠「どこでも IPv6 のみ」

**話すこと（訳）**
> 1 つ目のプラクティス：IPv6 は VPC 単位ではなく、サブネットの層ごとに決めます。
> エッジの層、つまりロードバランサーとエンドポイントはデュアルスタックのままにします。
> ワークロードの層は、依存先がすべて IPv6 で届くなら IPv6 のみにできます。
> だから ECR、ログ、S3 の VPC エンドポイントをデュアルスタックにしています。そうすれば IPv6 のみのタスクでも、NAT64 なしでイメージを取得できます。

### スライド 6 — 3 つを 1 枚で（5:00–6:30）

**スライド**
| | PrivateLink | VPC エンドポイント | VPC Lattice |
|---|---|---|---|
| 層 | L4 | L4 / ルート | L7 |
| 公開するもの | NLB のポート 1 つ | AWS の API | サービス / パス |
| 制御 | 承諾、SG | エンドポイントポリシー | 認証ポリシー、SigV4 |

**話すこと（訳）**
> 数字の前に、考え方を整理します。

> VPC エンドポイントは、同じ技術を AWS サービスに使うものです。大事なのはエンドポイントポリシーです。
> VPC Lattice はレイヤー 7 です。IAM 認証のあるアプリケーションネットワークです。
> 最後の行を覚えておいてください：提供側は、誰が呼んでいるかわかるでしょうか。

### スライド 12 — セキュリティ②：結果の表（13:00–15:00）

**スライド**
- `results/probe.csv` の表：trusted / 信頼しない SG / 未承諾 / iam-required
- ✓ 200、✗ 403、✗ timeout
- 意外な点：S3 ゲートウェイエンドポイントには SG がない

**話すこと（訳）**
> これが結果の表です。インスタンスも DNS も同じで、列ごとに 1 つだけ変えています。
> 信頼しないセキュリティグループでは、PrivateLink も Lattice もタイムアウトしました。
> 提供側がエンドポイントを承諾する前は、PrivateLink はまったく使えませんでした。
> Lattice のポリシーを「IAM 必須」にすると、匿名の呼び出しは 403、署名付きは 200 でした。
> 多くの人が驚く点：S3 ゲートウェイエンドポイントは ENI ではなくルートです。セキュリティグループはありません。ポリシーで守ります。

### スライド 13 — セキュリティ③：提供側から見えるもの（15:00–16:30）

**スライド**
- PrivateLink：`remote = NLB のアドレス`、ほかには何もない
- Lattice：リンクローカルの送信元 + `x-amzn-source-vpc` + `x-amzn-lattice-identity`
- → 呼び出し元ごとの認可には Lattice（または自前の mTLS / トークン）

**話すこと（訳）**
> いちばん好きなスライドです。提供側には実際に何が見えているでしょうか。
> PrivateLink の後ろのコンテナに見えるのは、ロードバランサーのアドレスです。誰が呼んだかはわかりません。
> Lattice の後ろでは、送信元の VPC が見え、SigV4 なら呼び出し元の IAM の識別情報も見えます。
> 提供側が呼び出し元ごとに判断する必要があるなら、PrivateLink ではその仕事をアプリに持たせることになります。Lattice ならネットワークが渡してくれます。

### スライド 14 ✂ — セキュリティ④：データ境界（16:30–17:30）

**スライド**
- バケットはエンドポイントを許可 ✓ だが、エンドポイントポリシーにない → 403
- インターネットから → 403
- エンドポイントポリシー = データをどこに出せるか、バケットポリシー = どこから読めるか

**話すこと（訳）**
> AWS サービスでは、エンドポイントポリシーが持ち出し対策になります。
> 「外部」のバケットは私のエンドポイントを許可していました。でもエンドポイントポリシーにそのバケットはありません。結果は 403 です。
> そしてインターネットからは、データ用バケットは 403 を返します。私のエンドポイント経由のリクエストしか受け付けないからです。

### スライド 15 — どう選ぶか（17:30–19:00）

**スライド**
- AWS の API にプライベートに届きたい → VPC エンドポイント（+ ポリシー）。S3 / DynamoDB はゲートウェイ
- 1 つの TCP サービスを多くのアカウントに公開、呼び出し元の識別は不要 → PrivateLink
- 多くのサービス、多くのチーム、呼び出し元ごとの認可、L7 のルーティング → VPC Lattice
- すべてに共通：エッジはデュアルスタック、ワークロードは IPv6 のみ、両ファミリーの SG ルール、ファミリーをログに残す

**話すこと（訳）**
> では、どう選ぶか。
> AWS の API には VPC エンドポイントを使い、エンドポイントポリシーを書きます。
> 1 つの TCP サービスを多くの利用者に公開するなら、PrivateLink がシンプルで速いです。
> 多くのチームの多くのサービスで、呼び出し元を知る必要があるなら VPC Lattice です。
> そしてどれでも：エッジはデュアルスタック、できればワークロードは IPv6 のみ、両ファミリーの SG ルール、アドレスファミリーがわかるログ。

### スライド 16 — まとめとリポジトリ（19:00–20:00）

**スライド**
- IPv6 前提：サブネットの層、デュアルスタックのエンドポイント
- 経路は「呼び出し元について何を知る必要があるか」で選ぶ
- ミリ秒を議論する前に接続の再利用を直す
- ハンズオン：github.com/MASAKIOKUDA-eng/AWS-ContainerNetwork-Research-handso（QR コード）

**話すこと（訳）**
> まとめは 3 つです。
> 1 つ目：IPv6 前提とは、サブネットの層ごとに設計し、依存先に IPv6 で届くようにすること。
> 2 つ目：経路は速さだけでなく、呼び出し元について何を知る必要があるかで選ぶこと。
> 3 つ目：経路より接続の再利用のほうが効くこと。
> ハンズオンは GitHub にあります。ぜひ試して、壊して、わかったことを教えてください。ありがとうございました！

## 質疑応答の準備

| 想定される質問 | 短い答え（英語で答える要点） |
|----------------|------------------------------|
| Transit Gateway ではだめなのか | TGW はネットワークをつなぐもので、サービスをつなぐものではない。重複しないアドレスが必要で、その上でサービス単位の制御も別に必要。広くつなぐには良いが今回の焦点ではない |
| Lattice は TCP に対応しているか | リソース設定経由で VPC のリソース（データベースなど）に対応、TLS パススルーのリスナーもある。今回は HTTP / HTTPS のサービスを測った |
| Lattice と PrivateLink のコストは | 課金モデルが違う。Lattice はサービスの時間・GB・リクエスト数、PrivateLink はエンドポイント × AZ の時間・GB と NLB。自分のリクエストの特性で計算する |
| PrivateLink で呼び出し元の IP を渡せるか | ターゲットグループで Proxy Protocol v2 を有効にし、アプリがそれを解釈すれば渡せる |
| ECS の IPv6 のみは本番で使えるか | 2025 年 9 月から対応。依存先（ECR、ログ、シークレット、自社の API）すべてに IPv6 かデュアルスタックの経路があるか確認する。IPv6 のみでは ECS Exec は使えない |
| なぜ CloudFormation ではなく cdkd なのか | 検証環境はその日のうちに何度も作って消す（デュアルスタック、IPv6 のみ、認証モード）。cdkd は同じ CDK アプリを SDK の直接呼び出しでデプロイするので、1 回ごとが短い。開発・検証用途向けで、本番では同じアプリを `cdk deploy` でデプロイする |
| IPv6 でインターネットに出るには | IPv6 は Egress-only インターネットゲートウェイ、NAT64 は DNS64 と NAT ゲートウェイ、検査は Network Firewall / GWLB。IPv6 の検査アーキテクチャの AWS ブログを参照 |
