## 2.2 設計の判断（とその理由）

| # | 判断 | 理由 |
|---|------|------|
| D1 | **インターネットへの経路を一切持たない**（IGW、NAT、EIGW なし） | 外に出る道は検証対象の経路だけなので、想定外のルートで結果が出ることがない。検証環境として最も安全な初期値でもある |
| D2 | **両 VPC の IPv4 CIDR を同じにする** | 3 つとも「ルーティング可能で重複しない IPv4」を必要としないことを示す。大きな組織で VPC ピアリングや TGW の妨げになる点 |
| D3 | **エッジのサブネットは常にデュアルスタック、ワークロードのサブネットは切り替え可能**（`WorkloadIpMode`） | NLB や多くのエンドポイントはサブネットに IPv4 アドレスがまだ必要。ワークロードは不要。「IPv6 前提だが、どこでも IPv6 のみではない」パターン |
| D4 | **1 つのタスク定義から 2 つの ECS サービスを作る** | イメージ、サイズ、AZ が同じなので、① と ② の違いはネットワーク経路だけになる |
| D5 | **両経路に HTTP リスナー + Lattice には HTTPS リスナーも追加** | HTTP どうしで公平に比べ、TLS のコストは別に測る |
| D6 | **負荷生成は EC2、接続は SSM のみ** | 再現しやすく、負荷生成側がボトルネックになりにくい。インバウンドのポートを開けない |
| D7 | **同じインスタンスに「信頼しない SG」を付け替える** | セキュリティのテストで変えるのは SG だけ。DNS、ルート、インスタンスはそのまま |
| D8 | **S3 の匿名読み取りを `aws:SourceVpce` で許可** | k6 から SigV4 なしで S3 を測れる。リソース側の境界の例にもなる。ブロックパブリックアクセスは有効のまま |
| D9 | **Flow Logs に `traffic-path`、`pkt-srcaddr`、`pkt-dstaddr`、`flow-direction` を含める** | 通信がどのアドレスファミリーで、どの経路を通ったかを示せる |
| D10 | **イメージはダイジェスト指定、非 root、ルートは読み取り専用、ケーパビリティ全削除、ECS Exec なし** | ECS ネットワークモード比較ハンズオンと同じコンテナの強化 |

## 2.3 IPv6 はどこで終わるか（重要なスライド）

| 区間 | `WorkloadIpMode=dualstack` | `WorkloadIpMode=ipv6only` |
|------|----------------------------|---------------------------|
| クライアント → インターフェイスエンドポイント（PL） | IPv6（k6 の `onlyIPv6`）または IPv4 | IPv6 |
| エンドポイント → NLB（PrivateLink の内部） | AWS が管理。ファミリーは利用側に従う | AWS が管理 |
| NLB → タスク | **IPv4**（ターゲットグループ `ipv4`、ECS はタスクの IPv4 を登録） | **IPv6**（ターゲットグループ `ipv6`） |
| クライアント → Lattice | IPv6（`fd00:ec2:80::/64`）または IPv4（`169.254.171.0/24`） | IPv6 |
| Lattice → タスク | **IPv4**（ターゲットグループ `IPV4`） | **IPv6**（ターゲットグループ `IPV6`） |
| クライアント → S3 ゲートウェイエンドポイント | エンドポイントが `dualstack` で、デュアルスタックの S3 名を使えば IPv6 | IPv6 |

> デュアルスタックの構成では、入口は IPv6 でも裏側はまだ IPv4 です。接続の層が変換してくれるので多くの場合は問題ありませんが、
> 設計レビューでははっきり言葉にしておきます。
> ハンズオンでの確認方法：提供側のアクセスログの `remote` と、Lattice のアクセスログの `targetIpPort`。

## 2.4 IPv6 を前提としたコンテナネットワーク設計のプラクティス（登壇の中身）

ハンズオンはこのプラクティスに沿って作っています。それぞれ、確かめられるシナリオを示します。

1. **VPC ではなくサブネットから考える。** すべての VPC に IPv6 /56 を付け、デュアルスタックか IPv6 のみかは *サブネットの層ごとに* 決める。エッジ層 = デュアルスタック、ワークロード層 = 依存先が対応していれば IPv6 のみ（`cfn/01-vpc.yaml`）
2. **依存先にまず IPv6 で届くようにする。** デュアルスタックのインターフェイスエンドポイント（`IpAddressType: dualstack`、`DnsRecordIpType: dualstack`）とデュアルスタックの S3 ゲートウェイエンドポイントがあれば、IPv6 のみのタスクも NAT64 なしでイメージ取得とログ送信ができる（S-3、`WorkloadIpMode=ipv6only`）
3. **インターネットが必要なら：IPv6 の外向きは EIGW、NAT ゲートウェイは NAT64 用（サブネットで DNS64）だけ。** 検査は Network Firewall や GWLB で両ファミリーに対して行う（このハンズオンではあえて作らない。[references.md](references.md) の IPv6 インターネット検査アーキテクチャのブログを参照）
4. **IP ファミリーの違いと IPv4 の重複は、接続の層で吸収する。** PrivateLink も Lattice も、ピアリングなしで IPv6 のクライアントから IPv4 で動くサービスに届く（2.3、X-6）
5. **提供側が呼び出し元について何を知る必要があるかで選ぶ**
   - 「このアカウント / VPC ならつないでよい」だけでよい → PrivateLink（承諾 + 許可するプリンシパル + エンドポイントの SG）
   - 「どのワークロードが呼んでいて、そのパスを呼んでよいか」→ SigV4 を使う Lattice の認証ポリシー
   - 「ここからどの AWS リソースに届いてよいか」→ エンドポイントポリシー（データ境界）
6. **制御を重ねる**：ネットワーク（エンドポイント / 関連付けの SG）→ 接続（承諾、認証ポリシー、エンドポイントポリシー）→ リソース（`aws:SourceVpce` 付きのバケットポリシー）。1 つの設定ミスですべてが開かないようにする（X-1〜X-5）
7. **セキュリティグループも IPv6 で書く。** `0.0.0.0/0` や VPC の CIDR で書いたルールには、`::/0` や IPv6 の CIDR の対になるルールが必要。Lattice のターゲットは `169.254.171.0/24` と `fd00:ec2:80::/64`（またはマネージドプレフィックスリスト）の両方を許可する（`TaskSg`）
8. **アドレスファミリーをログに残す。** Flow Logs の `pkt-srcaddr` / `traffic-path`、提供側のアクセスログ、Lattice のアクセスログで、本当に IPv6 で通っていることを示す（X-4）
9. **同じ負荷、同じ接続の方針で測る。** 接続の再利用や TLS のほうが、経路より効くことが多い（S-1 と S-2）
10. **つながるまでの時間も「スピード」に含める。** チケットと承認が要る経路は、0.3 ms 余計にかかる経路よりチームにとって遅い（S-6）

## 2.5 あえてハンズオンに含めていないもの

- Transit Gateway / VPC ピアリング（重複しないルーティング可能なアドレスが必要。このハンズオンはサービス単位の接続に絞る）
- Lattice のリソース設定 / サービスネットワークエンドポイント（データベースなどの TCP リソース）— 次のステップに適している
- AWS RAM によるクロスアカウント共有（簡単にするため 1 アカウントで実施。ポリシーはクロスアカウントでも同じ設計が使えるように書いている）
- インターネットへの外向き通信と検査（プラクティス 3 を参照）
